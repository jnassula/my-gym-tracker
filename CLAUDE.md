# myGymTracker — notes for Claude

Mobile-first gym tracker. FastAPI + Postgres + RustFS (S3) backend, React + shadcn frontend, all in Docker Compose. README.md has setup, commands and the auth design; this file holds the rules and the state of the work.

## Working rules (from the user)

- Work in phases. Finish one, show the result, **wait for "ok"** before starting the next.
- Small conventional commits per phase. Never push (the user pushes to `origin` on GitHub and rebases `main`). Work on a `feat/phase-N-*` branch created from `main`; list the phase's commits with `git log main..HEAD`.
- Write tests alongside the code. Run linters and tests before calling a phase done.
- Ask before adding dependencies outside the stack. Secrets only through env vars; never commit `.env`.
- At the end of each phase: update this file and give a 5-line summary (done, left out, decisions, how to test, next step).
- **Every deploy gets a new version, and nobody edits a version number** (the user's rule, 2026-10-02): CI works it out from the commits since the last release (see Production and CI/CD). So the commit type is not decoration: `feat:` for what a user can newly do (minor), `fix:`/`docs:`/`chore:`/`refactor:`/`test:` for the rest (patch), and `!` or a `BREAKING CHANGE:` line only for a change that breaks an installed app or a bridge already set up (major).

Dependencies the user approved (2026-09-28): TanStack Router, react-hook-form + zod, Phosphor icons, PyJWT, pwdlib[argon2], slowapi, email-validator, Mailpit (dev SMTP), `minio` (S3 SDK) + python-multipart, and (2026-09-28, phase 3 rework) `google-adk[openai]` to read PDFs with DeepSeek, the only LLM provider the user has. Phase 5 (2026-09-28): `recharts` via the shadcn chart component, for the progress charts. Phase 6 (2026-09-28): `vite-plugin-pwa` with `workbox-precaching` + `workbox-routing` (our own service worker), and `pywebpush` for Web Push (the user chose full Web Push in phase 6). Phase 8 (2026-09-29): `rustfs/rustfs` replaces MinIO (its community images were withdrawn from Docker Hub and quay.io; the user chose RustFS), Caddy is the HTTPS edge in production, and CI uses GitHub Actions pinned by commit SHA (checkout, setup-uv, setup-node, docker setup-buildx/build-push/login, CodeQL, dependency-review). pdfplumber is in the brief. Vitest/Testing Library/jsdom were added in phase 1 as test tooling. Phase 11 (2026-10-01): `pillow` as a direct dependency (it was already installed through pdfplumber), to decode and resize profile photos on the server. The user chose a "Mover para…" menu over drag-and-drop (no dnd-kit). Phase 18 (2026-10-02): no new dependency (shadcn `radio-group`, Base UI); phase 20 (2026-10-02): `fpdf2` writes the exported PDF on the server (the user chose it over reportlab and `@react-pdf/renderer`).

**Personal PDFs in `samples/` must never be committed** (they're in `.gitignore`); tests use the anonymised layout in `backend/tests/workouts/layout.py`.

## Commands

```bash
docker compose up --build                     # full stack (needs .env, copy from .env.example)
docker compose up --build -V frontend         # after package.json changes (renews node_modules volume)
docker compose exec backend pytest            # backend tests (own *_test DB, auto-created)
docker compose exec -e LLM_LIVE_TESTS=1 backend pytest -m llm   # real DeepSeek on samples/ (paid, minutes)
docker compose exec backend sh -c "ruff check . && ruff format --check . && mypy ."
docker compose exec backend alembic revision --autogenerate -m "..."
docker compose exec backend alembic upgrade head   # right after creating a migration: the dev backend reloads the models at once but only migrates when its container starts
docker compose exec backend python -m app.notifications.keys   # a VAPID key for .env (Web Push)
docker compose exec backend python -m app.admin.grant you@example.com [--revoke] | --list   # who may open the backoffice
docker compose exec backend python -m app.auth.email_samples you@example.com [pt|en|es]   # sample emails (Mailpit in dev)
docker compose -f deploy/compose.yml -f deploy/compose.build.yml up --build -d --wait   # the production stack locally (deploy/.env: DOMAIN=localhost, see deploy/README.md)
CURL_OPTS=--insecure sh deploy/smoke-test.sh https://localhost:8443 local   # what CI and each deploy check
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest   # lint the workflows after editing .github/
ngrok http --url=https://<name>.ngrok-free.app 5173   # the dev stack on a phone (DEV_ALLOWED_HOSTS in .env)
cd frontend && npm run lint && npm run typecheck && npm test && npm run build
```

Host ports (127.0.0.1): frontend 5173, backend 8200, Postgres 5440, RustFS (S3) 9100/9101 (API/console; bucket created on backend startup), Mailpit UI 8026. The defaults avoid ports other local projects already use (8000, 9000/9001, 5434, 8025).

## Backend conventions

- One folder per domain: `auth users workouts exercises logs files health body`, each with `router.py`, `schemas.py`, `models.py`, `service.py`. Extra modules are fine when they have a clear job (`auth/security.py` pure crypto, `auth/dependencies.py`, `auth/errors.py`, `auth/emails.py`). **Routers hold no business logic**: they parse input, call a service function and return a schema. Cookies, rate-limit decorators and status codes are HTTP concerns and stay in routers.
- Protected endpoints take `user: CurrentUser` (`app/auth/dependencies.py`). Every query filters by `user.id`. A user never sees another user's data. Tables without `user_id` (`workout_days`, `exercises`) are scoped by joining through `workout_plans`.
- Errors: services raise `AppError` subclasses with a specific `code` (auth ones in `app/auth/errors.py`). Every error body is `{detail, code}`; validation errors add `errors[]` and never echo the input. The frontend translates by `code`, so add new codes to `errors.*` in the locales.
- Rate limits: `@limiter.limit("…")` (`app/core/rate_limit.py`); the endpoint needs a `request: Request` parameter. Tests reset the limiter automatically.
- Email: depend on `Mailer` (`get_mailer`) and send from `BackgroundTasks`. Tests get an in-memory `outbox` fixture. Every email is plain text plus branded HTML: write the copy per language in the domain's `emails.py` and compose it with `branded_email` and the blocks of `app/core/email_layout.py` (`paragraph`, `checklist`, `countdown`, `button`, `note`; pure, they escape what they get). Mail clients rule the markup: tables, inline styles, no SVG, no web fonts, no `rgba`, always dark; the logo is a PNG inside the message (`cid:logo`, `app/core/assets/email-logo.png`). `build_mime` makes it multipart/alternative with the image related to the HTML. Sign-up sends the welcome (so a test that reads the outbox after `register` finds it first).
- Object storage: depend on `Storage` (`get_storage`, `app/core/storage.py`; any S3 through the `minio` SDK in a thread; RustFS in both Compose stacks, service `storage`). Tests get an in-memory `storage` fixture. Keys are `users/{user_id}/{kind}/{file_id}`; `files` rows record them. Uploads are read with a size cap (`files.service.read_upload`) and type-checked by bytes (`require_pdf`).
- Profile photo: `PUT`/`DELETE /api/users/me/avatar` (`users.service.set_avatar`). It is a `files` row of kind `avatar` that `users.avatar_file_id` points at (FK `SET NULL`, declared with `use_alter` because `files` points back at `users`), read through `/api/files/{id}/content`, so only its owner gets it; the backoffice never shows it. What is stored never depends on the client: `users/avatar.py` (`normalise`, pure, Pillow, run in `asyncio.to_thread`) decodes the upload (JPEG, PNG or WebP only), turns it upright by its EXIF orientation, puts transparency on white, crops the centred square, scales it down to at most 512 px (never up) and writes a JPEG without metadata. The upload is capped at 1 MB and at 16 megapixels by its header, checked before any pixel is decoded (a small file can claim a huge size); anything unreadable is 415 `unsupported_file_type`. Replacing or removing deletes the old row and object (`files.service.remove_file`, which leaves the commit to its caller). A new photo is a new file id. Tests build real pictures with Pillow (`tests/test_avatar_image.py`, `tests/test_avatar.py`).
- PDF reading (`app/workouts/parser`) is done by an LLM, not by rules (the user's decision). `extract.py` turns the PDF into text with pdfplumber (in `asyncio.to_thread`), in two views: layout text (keeps each exercise on its rest time's line) plus table cells when the PDF draws a grid (the only reliable way to map the summary's focus to its weekday; layout mode squeezes those columns together); `agent.py` runs a Google ADK `LlmAgent` over it through ADK's `OpenAILlm` pointed at DeepSeek (`LLM_*` settings); `output.py` validates and bounds the JSON reply (pure). DeepSeek is text-only and only guarantees `json_object` mode, so the agent has no `output_schema`: the shape is in `prompt.py` and validated with Pydantic. Thinking must stay off (`effort="none"` via `_EffortConfig`): at any other effort a week's plan takes 90–120 s and runs out of tokens. The instruction is a callable so ADK doesn't template the JSON example's braces. Services get the reader through the `get_plan_parser` dependency; tests override it with `FakePlanParser` (conftest) and `test_agent.py` drives the real agent with a scripted `BaseLlm`. conftest removes `LLM_API_KEY` from the environment so no test calls the API by accident; only `-m llm` with `LLM_LIVE_TESTS=1` does.
- Training log (`app/logs`): a session is one plan day on one date, the user's **local** date (`users.timezone`; `local_date` column, unique per user + day + date). The first set logged or exercise ticked starts it (`INSERT … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE` so concurrent taps get contiguous set numbers); "Terminar treino" sets `ended_at`, and a later set clears it. Emptying a session (last set deleted, tick removed) deletes it, so endpoints can answer `null`. "Last time" and history exclude today, and match an exercise by id or, for the trainer's next plan, by lower-cased name + muscle group (the group keeps a warm-up "Cadeira Extensora" apart from the working one); a session where the exercise itself was logged only shows its own sets. The clock is `logs.service.now()`: tests move it (`tests/logs/test_log_api.py`, `clock` fixture).
- Progress (`app/progress`, read-only, no models): follows an exercise across plans by `logs.service.exercise_key` (lower-cased name + muscle group) and leaves warm-up sets out of every figure. The arithmetic is pure in `progress/metrics.py`; `service.py` only loads rows (a user's whole log fits in memory). Definitions: a week streak counts consecutive Monday-to-Sunday weeks with at least one session, and the current week doesn't break it while empty; a record is a session whose heaviest set beats every earlier *date* (a first time isn't one); "1y" charts one point per week, "4w"/"3m" one per session; the week comparison is like-for-like (Monday up to today's weekday in both weeks); calendar "missed" means a weekday of the **active** plan since that plan was created, with no session. Plate maths is frontend-only (`features/training/plates.ts`).
- Plans are soft-deleted (`workout_plans.deleted_at`, set with `is_active = false`; the PDF is deleted). Plan queries filter `deleted_at IS NULL`; history and progress look exercises up with `logs.service.get_exercise(..., include_deleted=True)`, so logged weights outlive the plan.
- Notifications (`app/notifications`): Web Push through the `PushSender` dependency (`get_push_sender`): `WebPushSender` (pywebpush) when `VAPID_PRIVATE_KEY` is set, otherwise `DisabledSender` (`public_key` null, nothing scheduled). The browser key is derived from the private one (`public_key_of`). Texts per language in `messages.py`. A device is a `push_subscriptions` row unique by endpoint (a browser that signs in as someone else moves over); endpoints the push service reports gone are deleted. `scheduler.run_due(session, sender, at)` sends what is due at `at` in each user's time zone (training reminder within 3 h of its time, Sunday 20:00 summary, plan expiring in ≤ 14 days) and claims each one in `notification_deliveries` (unique user + kind + key, `ON CONFLICT DO NOTHING`) before sending; `run_forever` calls it every minute from the lifespan. The rest-end push is an in-memory asyncio timer per user (`service.schedule_rest_end`), lost on restart. Tests get a `push_sender` fixture (`FakePushSender`) and call `run_due` at fixed instants.
- Relationships use `lazy="raise"`: load collections with `selectinload` (see `workouts.service.get_plan`).
- Models: UUID primary keys (`UUIDPrimaryKey`), `timestamptz` everywhere (UTC). Enums are `str_enum(E)` (VARCHAR) paired with `enum_check(col, E)` in `__table_args__`. Don't use `Enum(create_constraint=True)`: Alembic autogenerate duplicates its CHECK. Autogenerate also misses new CHECK constraints: add them by hand.
- Weights are always stored in kg; `users.unit` is display-only. Emails are stored lower-cased (CHECK enforced).
- PDF export (`app/workouts/export.py`, pure; `GET /api/workouts/{id}/export.pdf?weights=`): A4 with fpdf2 and Inter embedded (`app/core/assets/fonts`, OFL, static instances of the frontend's font; the core fonts only know Latin-1). It writes what the parser was taught (`parser/prompt.py`): a heading per weekday ("Segunda Feira - Peitoral, Costas"), the warm-up as its own table whose rows also say "Aquecimento" under the name (a heading alone over several rows got them misread), then exercise / sets / rest in the trainer's words (`sets_text`: "3x12", "1x15, 1x12, 1x10", "30 min"; `format_rest`: "1 min e 30 seg", "entre 1 min a 2 min"). A weight goes next to the sets ("3x12 (52.5 kg)"), never into the name, which the parser takes as the words before the first set count; notes go under the name. `tests/workouts/test_export.py` reads the PDF back with pdfplumber, and its `-m llm` test has DeepSeek read an exported plan back exactly; run it after changing the layout or the prompt. The exercise key (`app/exercises/key.py`) lives apart from `logs.service` so `exercises.service` and `workouts.service` can import it without a cycle (the server failed to start once; tests import in another order).
- Exercise library (`app/exercises`, read-only, no new models): `GET /api/exercises/library` returns the user's exercises (plans not deleted, newest first; `last_weight` = the newest set logged on that key, deleted plans included) then the base list of `exercises/library.py` (≈150 by group, named in `user.language`; long lines allowed there), one entry per `logs.service.exercise_key`. The client searches it (a few hundred rows), the server doesn't.
- Register new model modules in `app/models.py`, otherwise Alembic won't see them.
- `GET /health` (root) is the healthcheck; `release` is the commit the production image was built from (`APP_RELEASE`) and `version` its version (`APP_VERSION`), both `dev` elsewhere. The data sources domain lives under `/api/health/*`.
- Settings (`app/core/config.py`): with `ENVIRONMENT=production` the app refuses to start when a secret still has a `change-me` example value, `COOKIE_SECURE` is off or `FRONTEND_URL` isn't https (`tests/test_config.py`).

- Data sources (`app/health`): the web has neither HealthKit nor Health Connect, so each source (`HealthProvider`: `apple_health`, `health_connect`) has a bridge on the phone that posts to the same `POST /api/health/sync`, authenticated by that source's token (`health_connections`, one row per user and provider, `token_hash` SHA-256; `dependencies.get_health_connection`, not a session). The token's provider picks the payload reader (`schemas.PARSERS`), and both readers give `service.store` the same samples by type.
  - Apple Health: an iPhone shortcut (built by hand from the steps in the app) sends heart rate (`hr_t`/`hr_v`) and active energy (`ae_t`/`ae_v`) of the last 3 days, and optionally body mass (`bm_t`/`bm_v`, with the Health app's unit in `bm_u`: kg, lb or st, kg when left out) and body fat (`bf_t`/`bf_v`, a fraction or a percentage), as parallel lists: JSON arrays, or text with one item per line (a list variable in a Text field), a lone item as itself, numbers as text (decimal comma too), dates ISO 8601 with offset (`SyncBatch`; parse errors never echo the value). It sends everything again on every run.
  - Health Connect: the HC Webhook Android app (open source, not ours; payload in its `docs/webhook.md`) posts `heart_rate[{bpm, time}]`, `active_calories[{calories, start_time, end_time}]`, `weight[{kilograms, time}]` and `body_fat[{percentage, time}]` among kinds the app ignores (`HealthConnectBatch`). It sends each sample **once**, so a recent sample outside every session is kept without a session (`service.SENT_ONCE`, `WAIT` = 3 h) until a session's window reaches it; `service.sweep` (every minute, `health/sweeper.py`, started in the lifespan) joins what can be joined and deletes the rest. Energy over an interval is stored as one sample per minute (`metrics.spread`), so a session gets only the minutes inside it; intervals over 4 h (day totals) are dropped.
  - Only samples inside a session's window are kept (`metrics.session_window`: 5 min before the first set to "Terminar treino", or 3 min after the last set, capped at 20 min), upserted by user + type + instant because runs overlap; out-of-range values are dropped. **A session takes each kind of data from one source, the first to send it** (`service._holders`): a watch that writes to both health apps would otherwise count its calories twice, and the unique index has no source in it (the previous release's upsert names its three columns; widen it only in a later release). `health_samples.source` says who sent a sample: turning a kind off or disconnecting deletes that source's samples only. A sync and a sweep lock the user row, since both decide by what the sessions hold.
  - Endpoints: `GET /api/health/connections`, `POST`/`DELETE /api/health/connections/{provider}`, `PATCH …/settings`. The old `GET /api/health`, `/connection`, `/settings` remain as Apple Health's (`deprecated`), for installed apps that haven't updated: remove them a release later.
  - Neither bridge sends the watch's workouts, so `HealthSampleType.DURATION` is unused and a session's duration is the app's own. A session's detail (`GET /api/progress/sessions/{id}`) adds the watch figures (average/max heart rate, calories, a ≤ 90-point chart series, each exercise's peak 90 s before to 30 s after its sets). Tests: `tests/health/` (the `clock` fixture moves this domain's clock too).
  - Garmin has no API for individuals (business only): its app writes into Apple Health and Health Connect, so it is a guide in the frontend, not a provider. Strava is a "coming soon" row (its 2026 API terms cap retention at 7 days).
- Body (`app/body`): weighings (`body_measurements`), typed in (`manual`: a local `day`, stored as now for today and as that day's noon in the user's time zone otherwise; typing a day again replaces it) or read from a smart scale in the browser (`scale`: always "now", the scale's own clock is often wrong; with the impedance when it measured one). Always kg. **What is stored is the reading; the body composition is worked out on read** (`composition.compose`, pure) from the weight, the impedance and the profile's `height_cm`, age on that day (`birth_date`) and `sex`, so correcting the profile corrects every past weighing; without all three, or without an impedance, a weighing shows the weight alone (plus BMI with a height, and a `body_fat_pct` typed in). The formulas are the Mi Fit ones, ported from the MIT-licensed `lolouk44/xiaomi_mi_scale` (notice in `composition.py`; openScale's are GPL, don't copy them) and tested against that code's own results (`tests/body/test_composition.py`); out of their bounds (`MAX_HEIGHT_CM` 220, 10–200 kg, age ≤ 99, impedance ≤ 3000) they give nothing. `GET /api/body?range=` gives the latest weighing of all time, the range's weighings and the chart points (`metrics.py`, pure: a day's last weighing; over a year, the week's average from Monday), by the user's local day. The backoffice never reads any of it, nor the three profile fields. `UserUpdate` takes null for those three only (`CLEARABLE_FIELDS`). Weighings also come through the data sources (`apple_health`, `health_connect`: the scale's own app writes them into the phone's health app): `health.service.sync` hands a bridge's weights and body fats to `body.service.take` when the connection's `body` switch is on. `metrics.pair` joins each weight with the body fat measured with it (within 2 min); `metrics.same_weighing` (within 10 min and 0.15 kg) leaves out one that is already here from another source (read over Bluetooth and sent later by the scale's app, or sent by both health apps); out-of-range weights and dates ahead are dropped. A bridge's weighing the user deletes is hidden (`deleted_at`), not removed, because the shortcut sends its last days again on every run; every read filters `deleted_at IS NULL`. The API itself only accepts `manual` and `scale`. Turning the switch off or disconnecting deletes that source's weighings (`body.service.forget`). `body` must not import `progress.service` (it imports `health.service`, which imports `body`): `RANGE_DAYS` lives in `progress.schemas`.
- Backoffice (`app/admin`, read-only, no models): the only domain that reads across users, so it returns counts and account data (name, email, dates) and never plans, PDFs, weights or health samples; keep it that way. Endpoints take `CurrentAdmin` (`admin/dependencies.py`): the accounts with `users.is_admin`, read on every request (revoking is immediate), 403 `forbidden` otherwise; `UserRead.is_admin` tells the frontend. An account becomes an administrator only on the server, with `python -m app.admin.grant` (`admin/grant.py`: `run()` holds the logic, `service.set_admin` the write) and never through the API: sign-up doesn't verify emails, so the right belongs to an account, not to whoever holds an address. (It used to be a list of addresses in `ADMIN_EMAILS`, with sign-up refusing them; on a new server that left the owner unable to register. The `administrators` migration promoted the listed accounts once.) "Active" = logged a workout in the period. Tiles compare rolling periods (7/30 days by instant); the chart's buckets are the administrator's days, weeks (Monday) and months for sign-ups, and each workout's own `local_date` for activity. Buckets are grouped in SQL by label (`_by_bucket`: repeating the expression binds its parameters twice and Postgres rejects the GROUP BY) and filled in `admin/metrics.py` (pure). Closing accounts (`PATCH`/`DELETE /api/admin/users/{id}`): deactivating sets `users.deactivated_at`, revokes every refresh token and is refused everywhere an account comes in, so **any new way in must check `deactivated_at`**: `auth.service.authenticate` (401 `token_revoked`: signed out at once), `login` (403 `account_disabled`, only after the right password), `refresh`, password reset (no email, old links refused), the data sources' tokens and the scheduler. Deleting removes the PDFs from object storage first (a failing storage deletes nothing and the deletion can be retried), then the user row; every table cascades. Administrators' accounts are protected (403 `admin_account_protected`), the caller's own included. Each action is logged with both ids. Tests (`tests/admin/`) sign the administrator up and call `tests.helpers.make_admin` (the `admin` fixture).

## Frontend conventions

- Design: `design/README.md` (Nocturne on shadcn tokens). The canvas is `design/myGymTracker.dc.html`; it ends with a per-screen list of shadcn components. Follow it screen by screen.
- Use shadcn components (Base UI, `base-nova` style, `iconLibrary: phosphor`) whenever one exists: `npx shadcn@latest add <name>`. `src/components/ui/*` is generated. The only design-system edits are to `button.tsx` (variant `outline-primary`; sizes `touch` 48px, `hero` 52px, `icon-touch` 44px), to `input.tsx`/`input-group.tsx` (h-12, `bg-card`) and to `slider.tsx` (`thumbLabel`: the generated thumb has no accessible name). Re-apply these if a component is re-added with `--overwrite`. When `add` asks to overwrite `button.tsx`, answer **no** (`printf 'n\n' | npx shadcn@latest add <name>`).
- Generated shadcn controls are small (`SelectTrigger` h-8, menu items py-1): pass `h-12`/`min-h-11` at the call site. `DialogContent` has an English "Close" label: use `showCloseButton={false}` with a translated button.
- Extra tokens beyond shadcn's: `--warning` (low-confidence parse flags, from the design) and `--heart` (heart rate: the design's `#e07a86`, stepped to `#d9707d` in dark to pass the dataviz validator; `#b8505d` in light).
- Logo: "Anilha G" (`design/logo/`, described in `design/README.md`). Use `LogoMark` (`src/components/logo-mark.tsx`, `currentColor`); don't redraw it. `public/favicon.svg` is a copy of `design/logo/favicon.svg`.
- When styling a `Link` as a button, wrap in `cn(buttonVariants(...))`: `buttonVariants` alone doesn't resolve Tailwind conflicts.
- No custom CSS outside the Tailwind/shadcn tokens in `src/index.css` without a stated reason. Icons from `@phosphor-icons/react`.
- Settings (`features/settings`): rows from `rows.tsx` (`SettingsGroup`, `SettingsRow`, `SwitchRow`, `LinkRow`, `Segmented`). `useUpdateMe` is optimistic and merges only the fields it changed into the cached user, so a slow reply can't undo a newer change.
- Profile photo (`features/settings`): show it with `UserAvatar` (Início, Definições, Perfil), never a bare `Avatar`. A chosen picture opens `PhotoEditor` ("Ajustar foto"): drag, zoom up to 4× (pinch, wheel, slider, buttons, `+`/`−`) and quarter turns. The rules are pure in `avatar-crop.ts` (a window on the picture: `panBy`, `zoomTo` around an anchor, `turn`, `cropRect`); `avatar.ts` is the browser's part (`loadPicture` reads the file upright and scales it to a 2048 px working copy so dragging stays smooth, `turnPicture`, `paint`, `toJpeg`). The preview and the saved photo are drawn by the same `paint` from the same `cropRect`, so what is saved is what was shown; keep it that way. jsdom has no canvas: screen tests mock `avatar.ts` and assert on the rectangle it is asked to draw; pointer, pinch and wheel were checked in a real browser. The upload only saves bandwidth, the server normalises again. The photo needs the session, so `avatarQuery` fetches it and keeps an object URL in the query cache by file id (`staleTime`/`gcTime` infinite); `useSetAvatar` seeds the cache with what it just sent and both mutations release the old URL (`forgetAvatar`). Base UI's `AvatarImage` only renders once the picture loaded, and its slider thumb is `visibility: hidden` without layout: in jsdom assert on requests and on the session's `avatar_file_id`, and reach the slider with `getByLabelText`.
- Regional formats: every `Intl` call takes `intlLocale()` (`src/i18n`: pt → pt-PT, en → en-GB, es → es-ES), never `i18n.language` directly. Short dates use `formatDayMonth`.
- Dark is the default theme (`next-themes`, key `mygymtracker-theme`; `class="dark"` preset in `index.html`).
- The phone's status bar overlays the installed app (`viewport-fit=cover`, `black-translucent`): every screen's top padding is the inset **plus** a margin, `pt-[calc(env(safe-area-inset-top)+0.75rem)]` (`Page`, Início, the auth screens, the backoffice), never `max(inset, margin)`, which put the title flush against the bar and clipped it on real phones (the user's report, 2026-10-02); the toaster gets the same offset. Keep that form for any new top-anchored element.
- Touch targets ≥ 44px. Filled `primary` only for the one hero action per screen; other actions are `outline-primary`.
- **No hardcoded strings**: everything goes through i18next (`src/i18n/locales/{pt,en,es}.json`, keys typed from `pt.json`). A test enforces key parity across locales. Form error messages are translation keys (zod messages such as `validation.email`, server errors such as `errors.<code>`), translated at render.
- Routing: TanStack Router, file-based (`src/routes`, generated `routeTree.gen.ts` is committed). `_auth/*` is guest-only and `_app/*` needs a session. `reset-password` is unguarded because it is an email deep link.

## Production and CI/CD

- `deploy/` is the production stack (runbook: `deploy/README.md`). `compose.yml` pulls `ghcr.io/jnassula/my-gym-tracker/{backend,frontend}:<commit sha>` (`IMAGE_TAG`, written into the server's `.env` by `deploy.sh`); `compose.build.yml` builds the same images from source (local runs; it replaced `docker-compose.prod.yml`). Caddy (80/443, Let's Encrypt) → nginx (`frontend/nginx/`) → backend; Postgres, RustFS and the `backup` service sit on the internal `data` network. Every service has rotated logs.
- `deploy.sh <sha>`: validates `.env`, pulls, dumps the database, `up --wait`, and on failure starts the previous tag again; then reloads Caddy and prunes old images by the `mygymtracker.image` label. `backup.sh` (daily dump + RustFS data tar, `now`/`db` modes), `restore.sh <dump> [files]`, `smoke-test.sh <url> [release [version]]`, `version.sh [commit]`. All POSIX sh, checked with shellcheck (`koalaman/shellcheck`).
- Versions: `deploy/version.sh [commit]` prints a commit's version from the history: its own `vX.Y.Z` tag if it has one, otherwise the last tag before it raised by its commits (`type!:` or `BREAKING CHANGE:` → major, `feat:` → minor, anything else → patch), `1.0.0` with no tag yet. It needs the full history (`fetch-depth: 0`, `fetch-tags`). CI's `images` job runs it (after `deploy/version-test.sh`, its self-test on a throwaway repository) and bakes the result into both images as the `APP_VERSION` build argument: the backend reports it in `/health`, the frontend gets it as `VITE_APP_VERSION` (`src/lib/version.ts`, shown under Definições) and writes it into the page (`<meta name="app-version">`, a small plugin in `vite.config.ts`), and `smoke-test.sh <url> <release> <version>` checks both. `deploy.yml` reads the version back from the live `/health` once the site is healthy and, if `v<version>` isn't a tag yet, creates it with a GitHub release (`gh release create`, `contents: write` on that job and on CI's caller job). So a failed deploy uses no number up, and a rollback (an older image, with its version inside) creates nothing. The version in `pyproject.toml`/`package.json` is not the app's. A tag pushed by the workflow doesn't start a CI run.
- **A rollback swaps images but never undoes migrations**: every migration must keep the previous release working (add first, drop in a later release).
- A new setting is an env var in three places: `.env.example` (dev), `deploy/.env.example`, and the backend `environment` of `deploy/compose.yml` (and `docker-compose.yml`).
- Server-specific files never come from the repo and the deploy never overwrites them: `.env`, `compose.override.yml` (extra networks, e.g. for other apps' containers), `caddy/sites/*.caddy` and `caddy/global/*.caddy` (other sites this Caddy serves; the Caddyfile imports them). Never put server specifics (other apps, IPs) in this public repo.
- CI (`.github/workflows/ci.yml`): backend (ruff, mypy, pytest against a Postgres service), frontend (oxlint, tsc, Vitest, build, route tree committed), then `images` builds both production images and runs the real `deploy/compose.yml` on the runner (Caddy on localhost) with `smoke-test.sh`, a sign-up, the HTTPS redirect and a backup. On `main`: images pushed to GHCR, then `deploy.yml` (also `workflow_dispatch` with a SHA to roll back) over SSH as `deploy` with a pinned host key; skipped until the `DEPLOY_HOST` variable exists. `codeql.yml` weekly and on PRs; Dependabot weekly (no Postgres majors; Python/Node versions by hand with `.python-version` and CI's `node-version`).
- Actions are pinned by full commit SHA with the version in a comment; Dependabot updates both. Run actionlint after editing workflows.
- nginx resolves `backend` through Docker's DNS on every request (`resolver 127.0.0.11`, `proxy_pass $backend`), so a recreated backend never gets 502s. Security headers live in `frontend/nginx/security-headers.conf`, included by every `location` that sets its own `add_header` (nginx drops inherited headers otherwise). HSTS is Caddy's. The CSP is **report-only** until checked on real phones.
- The backend runs one uvicorn worker on purpose (the scheduler, rate-limit counters and rest timers are in-process), started with `exec` so it gets SIGTERM.

## Data model

Migrations: `initial schema` (all tables), `auth password tracking and persistent sessions`, `files, plan source file and exercise rest`, `session local date and done exercises`, `user auto rest preference`, `soft delete workout plans`, `push notifications`, `apple health connection`, `user deactivation`, `profile photo`, `administrators`, `data sources`, `body measurements`, `body data sources`. Differences from the original brief:

- `workout_sessions` added: `health_samples.session_id` needed a target, and progress is aggregated per session.
- `exercise_logs.session_id` added (NOT NULL).
- `order` renamed to `position` (reserved word in SQL).
- `workout_days.weekday` is nullable for plans that rotate A/B/C instead of using weekdays.
- `exercises.reps` is text ("8-12", "10/8/6"); `sets`/`reps` are nullable because PDFs don't always include them.
- `refresh_tokens.family_id` (rotation with reuse detection) and `refresh_tokens.persistent` ("remember me").
- `users.password_changed_at`: access tokens issued earlier are rejected. JWT `iat` is a float for sub-second precision.
- Partial unique index: at most one active plan per user.
- No table for password-reset tokens: they are signed JWTs carrying a fingerprint of the password hash, so they become single-use once the password changes.
- `files` table (uploads exist before the plan they produce); `workout_plans.source_file_id` (FK, SET NULL) replaces `source_file_key`; `workout_plans.valid_until` ("Trocar até").
- `exercises.rest_seconds`/`rest_max_seconds` (the rest timer in phase 4 needs them) and `exercises.muscle_group` as a key enum.
- `workout_sessions.local_date` (the user's date; unique per user + day + date) and `workout_sessions.done_exercise_ids` (UUID[]; exercises ticked off without sets, such as a treadmill warm-up).
- `users.auto_rest` ("Descanso automático") and `workout_plans.deleted_at` (soft delete).
- `push_subscriptions`, `notification_settings` (one row per user, written on the first change; defaults until then) and `notification_deliveries` (each scheduled reminder claimed once).
- `users.deactivated_at` (set from the backoffice; null = active).
- `users.avatar_file_id` (FK to `files`, SET NULL) and `avatar` as a third kind of file.
- `users.is_admin` (the backoffice; set with `app.admin.grant`).
- `body_measurements` (weighings: instant, source `manual`/`scale`/`apple_health`/`health_connect`, weight in kg, the scale's impedance, a typed-in or reported body fat, `deleted_at` for a bridge's weighing the user deleted; unique per user + source + instant), `health_connections.body` (the weighings switch) and `users.height_cm`, `users.birth_date`, `users.sex` (optional, for the body composition).
- `health_connections` (one per user and provider, primary key on both: the bridge's token hash, last sync, which kinds to keep), `health_samples.source` (the provider that sent it) and a unique index on `health_samples` (user, type, instant) so re-sent samples update. `provider` and `source` keep a server default of `apple_health` while a release without them may still run.

- Versions: the tagging step in `deploy.yml` has only run through actionlint, never on GitHub (it needs a real deploy): check the first one creates `v1.0.0` and its release. A branch's build computes a version too (the one it would get), without publishing or tagging it. Release notes are GitHub's generated ones, which list pull requests: with direct pushes to `main` they are little more than a link to the changes.

- Weighings through the bridges were tested against the documented payloads and the live API with `curl`, not on real phones: whether Zepp Life / Mi Fitness write body fat (or only weight) into the Health app and into Health Connect, what the shortcut's "Unit" gives for body mass (`KG_PER_UNIT` in `health/schemas.py` knows kg, lb, lbs, st; anything else is a 422), and the Health app's type names in the optional steps (`health.setup.steps.weight`/`bodyFat`). A weighing that arrives through a bridge has no impedance, so it shows the weight and the body fat the scale's app worked out, not the full composition.

- The scale was never read for real: the frame's layout comes from two independent open-source readers (lolouk44/xiaomi_mi_scale, WebBodyComposition) and the flow was tested with a stand-in scale. Weigh on the real one in Chrome (Android over HTTPS, or a computer on localhost) and compare with the Zepp Life app; if the weight or the composition differs, the fix is in `scale-frame.ts` or `composition.py`. Zepp Life must be closed (one connection at a time). With the scale set to lb or jin the frame is converted, also unverified. `Permissions-Policy` now allows `bluetooth=(self)` in production.
- Body: no editing of a weighing (delete and add again), no goal weight, height only in cm, no export. Designed (profile's "Peso corporal | Altura" inputs) but built differently: the weight is a history under Progresso, not a profile field. Not in the design canvas (built from the tokens and the dataviz rules).

- Health Connect was tested against the payload in HC Webhook's docs (and the live API with `curl`), not yet with the app on a real Android phone: check the real payload's size against the 16 MB cap (a watch that writes heart rate every second sends about 8 MB on the first sync), that "Completo" is how the app names the resolution in the user's language, and that Garmin Connect really writes heart rate and active calories into Health Connect and Apple Health as the guide says (`sources.garmin.*`). HC Webhook also has an iPhone app (same payload): it could replace the hand-built shortcut one day.
- Samples waiting for a session stay up to 3 hours in the database (Health Connect only); the intro says so. A source that syncs after another already filled a session is ignored for that session, even if the first is disconnected later (the shortcut sends again; HC Webhook doesn't).
- The old `/api/health`, `/api/health/connection` and `/api/health/settings` paths are deprecated aliases for Apple Health: remove them (and `HealthRead`, `service.read`) once every installed app has updated. The `apple_health` server defaults on `health_connections.provider` and `health_samples.source` can go in the same later release.

- `ADMIN_EMAILS` is still passed to the backend in both Compose files, only for the `administrators` migration to read once. When every environment has run it, remove the two lines (and the variable from the servers' `.env`).

- Profile photo: the editor moves, zooms and turns by quarter turns; no free rotation, mirroring, filters or brightness, and a saved photo can't be reopened to adjust (the original isn't kept: choose the file again). At the deepest zoom a small picture gives a small photo (it is never scaled up). HEIC only works where the browser decodes it (Safari); elsewhere the screen says the image couldn't be read. Checked in Chrome with mouse, wheel and emulated touch, not yet on a real iPhone (camera roll, "Tirar foto", pinch).

- Emails were checked in Chrome and Mailpit (its HTML check: 93% of the markup supported everywhere, the rest degrades: square corners and no glow in Outlook for Windows), not yet in real inboxes: send the samples to Gmail, Apple Mail and Outlook accounts through the production SMTP, and look at them in Gmail's dark and light modes. Not in the design canvas (built from the tokens and the app's screens).
- The welcome email goes to an address nobody verified (sign-up doesn't confirm emails), so a mistyped address welcomes a stranger; its footer says why it was sent. Email verification is not built.
- Backoffice: no export, no filter by status, and nobody is emailed when their account is deactivated or deleted. Deleting an account removes the objects that have a `files` row; an upload whose row was never written (a failure between the two) would stay in storage. "Last seen" is the last workout: sign-ins aren't recorded (refresh tokens are deleted as they expire). Figures are computed on each request, fine for thousands of accounts; cache or pre-aggregate if it ever gets slow. Not in the design canvas (built from the existing tokens and the dataviz rules).
